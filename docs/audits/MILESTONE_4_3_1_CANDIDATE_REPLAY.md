## 1. Executive Summary

Milestone 4.3 evaluated entry filters by post-processing an already-completed trade ledger (`entry_diagnostics.csv`), dropping losing trades retroactively. This audit milestone (**Milestone 4.3.1**) remediates that methodological defect by embedding the entry-filter evaluation **directly into the event-driven simulation loop of `HistoricalBacktestEngine`**.

### Key Architectural Remediation:
1. **Pre-Risk Manager Filter Gating**: Candidate setups generated by `StrategyAnalyst` at candle $T$ close are now evaluated by `_evaluate_candidate_filter(...)` **before** being submitted to the Risk Manager.
2. **Dynamic Slot Unblocking**: If a filter rejects a candidate, the portfolio position slots (capped at 2) remain unblocked, allowing the engine to consider subsequent valid market setups.
3. **Pipeline Telemetry Instrumentation**: Full accounting of the signal funnel:
   - `candidate_signals`
   - `filter_accepted_signals`
   - `filter_rejected_signals`
   - `risk_approved_signals`
   - `risk_rejected_signals`
   - `executed_trades`

## 2. Architecture & Decision Flow

### The Remediated Signal Pipeline

```
[StrategyAnalyst @ Candle T Close]
             │
             ▼
     Candidate Signal
             │
             ├──► [Entry Filter Gate: H1...H7]
             │           │
             │           ├──► REJECTED ──► Filter Rejection Metric Incremented
             │           │                 (Position slot preserved; no cash allocated)
             │           ▼
             │       ACCEPTED
             │           │
             ▼           ▼
[Risk Manager: Concurrent Limits & Sizing (Rule S-04)]
             │
             ├──► REJECTED ──► Risk Rejection Metric Incremented (slots full / drawdown limit)
             │
             ▼
         APPROVED
             │
             ▼
[PaperExecutionSimulator: Next-Candle-Open Execution (Rule A-10)]
```

### Code Implementation (`backend/app/simulation/engine.py`):
```python
if strat_out.output.evaluation_outcome in ("LONG", "SHORT") and strat_out.output.candidates:
    cand = strat_out.output.candidates[0]
    pipeline_counts["candidate_signals"] += 1

    # Candidate-level filtering before Risk Manager (Milestone 4.3.1)
    if self.config.entry_filter:
        htf_series = htf_candles_by_symbol.get(sym) if htf_candles_by_symbol else None
        filter_passed, filter_reason = self._evaluate_candidate_filter(
            cand=cand,
            candles=sub_candles,
            curr_ts=ts,
            htf_candles=htf_series,
        )
        if not filter_passed:
            pipeline_counts["filter_rejected_signals"] += 1
            continue
        pipeline_counts["filter_accepted_signals"] += 1
    else:
        pipeline_counts["filter_accepted_signals"] += 1

    # Pass through Risk Manager (Rule S-04)
    risk_eval = self.risk_manager.evaluate_signal(...)
    if risk_eval.approved and risk_eval.position_size:
        pipeline_counts["risk_approved_signals"] += 1
        new_pos = self.execution_simulator.simulate_entry(...)
    else:
        pipeline_counts["risk_rejected_signals"] += 1
```

## 3. Methodological Comparison: Post-Hoc Ledger Pruning vs True Replay

| Evaluation Dimension | Post-Hoc Trade Ledger Pruning (Milestone 4.3) | Candidate-Level Event Replay (Milestone 4.3.1) |
| :--- | :--- | :--- |
| **Point of Evaluation** | After baseline simulation finishes, applied to completed trade CSV rows | Inside simulation event loop at candle $T$ close |
| **Portfolio Slot Dynamics** | Rigid; blocked slots in the baseline remain "empty" when a trade is pruned | Dynamic; rejected candidate leaves slot open for subsequent setups |
| **Alternative Candidates** | Ignored (0 alternative candidates can be evaluated) | Fully considered and executed if valid |
| **Capital Path Dependency** | Static equity; ignores compounding changes from unexecuted trades | Dynamic equity; available cash accurately determines position size |
| **Risk Manager Sequencing** | Evaluated on trades Risk Manager ALREADY approved in the baseline | Evaluated BEFORE Risk Manager, preserving risk authorization integrity |
| **Scientific Validity** | **Defective** (optimistic selection bias on historical ledger) | **Rigorous** (true historical path simulation) |

### Telemetry Insights:
1. **The Signal Funnel**: Out of 358 raw setups fired by `StrategyAnalyst`, the unfiltered baseline executed 277 trades because 81 candidates were blocked by the `max_concurrent_positions = 2` cap or symbol-lock.
2. **Aggressive Pruning by H7**: The Confluence Ensemble filtered out **75.4% of all candidate signals** (270 out of 358), permitting only 88 setups to reach the Risk Manager.
3. **Risk Approval Parity**: Of the 88 filter-accepted setups, Risk Manager authorized 65 trades, rejecting 23 due to temporary concurrency or daily drawdown limits.

### Critical Finding on H7 Replay Concurrency:
- In this specific historical dataset, the 65 trades executed under Candidate Replay were identical to the 65 trades retained under Post-Hoc Pruning.
- **Why?** Because H7 filters out so many signals (75.4% rejection rate), the surviving trades were sufficiently sparse in time that they rarely competed for concurrent slots.
- However, the crucial difference discovered by our audit is that **the post-hoc method was a procedural risk**, not an empirical invalidation of the numbers themselves.
- The real vulnerability of H7 lies not in slot branching, but in **timeframe clustering and OOS inactivity**, detailed in `MILESTONE_4_3_1_TEMPORAL_INTEGRITY.md`.
